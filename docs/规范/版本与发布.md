# 版本与发布

基准：v1.0.0 / 2026-11-11

## 版本号

版本号遵循[语义化版本](https://semver.org/lang/zh-CN/)，格式是 `主版本.次版本.修订号`。

| 改动 | 升哪一位 |
|---|---|
| 修复问题，用户看到的功能不变 | 修订号 |
| 新增功能，原有用法不受影响 | 次版本 |
| 去掉功能，或者原有用法要改 | 主版本 |

`package.json` 的 `version` 是版本号的唯一来源。页面设置里显示的版本号在构建时从它读取。

## 分支和标签

- `main` 是唯一的长期分支，上面的每个提交都要能通过检查。
- 每次发布对应一个标签，名字是 `v` 加版本号，例如 `v1.2.0`。
- 标签名带连字符的是预发布版，例如 `v1.3.0-beta.0`。不带连字符的是正式版。

## 流水线

| 触发条件 | 工作流 | 做什么 |
|---|---|---|
| 推送到 `main`，或者提交 Pull Request | `.github/workflows/ci.yml` | 类型检查、测试、构建 |
| 推送正式版标签 | `.github/workflows/release.yml` | 类型检查、测试、构建 → 创建 GitHub Release → 更新 GitHub Pages |
| 推送预发布版标签 | `.github/workflows/release.yml` | 类型检查、测试、构建 → 创建标记为预发布的 GitHub Release；不更新 GitHub Pages |

- GitHub Pages 只在发布正式版时更新。推送到 `main` 不会改变线上页面。
- 每个 Release 附带构建产物的压缩包 `tunepick-<标签>.zip`，解压后可以放到任意静态服务器上。
- Release 的说明取自 `CHANGELOG.md` 里对应版本的那一节。

发布流水线会检查两件事，任何一件不满足就失败，不会产生 Release：

1. 标签里的版本号和 `package.json` 的 `version` 一致。
2. `CHANGELOG.md` 里有这个版本的一节，并且内容不为空。

## 发布步骤

1. 在 `CHANGELOG.md` 顶部加上新版本的一节，标题格式是 `## [1.2.0] - 2026-12-01`，写清楚用户能感知到的变化。提交。
2. 升版本号。这条命令会改 `package.json`、提交、并打好标签：

   ```sh
   npm version patch   # 或 minor、major
   ```

3. 推送提交和标签：

   ```sh
   git push --follow-tags
   ```

4. 在仓库的 Actions 页面等 Release 工作流跑完，然后打开线上页面确认设置里的版本号已经更新。

发预发布版时，第 2 步改用：

```sh
npm version prerelease --preid beta
```

## 仓库设置

发布流水线依赖下面两项仓库设置：

- Settings → Pages 的 Source 是「GitHub Actions」。
- Settings → Environments → `github-pages` 的部署规则允许 `v*` 标签。GitHub 默认只允许默认分支部署到这个环境，不加这条规则，标签触发的部署会被拒绝。
